## 1. Instrumenter (CLI)

- [x] 1.1 Project and config.
  - `findProject(cwd)` (`cli/src/project.js`) walks up to the nearest folder with `jstrace.config.json` or `.jstrace/`, else takes the start folder. `relative()` gives project-relative `/` paths, refusing ones outside the project or in `.jstrace/`.
  - `loadConfig()` (`cli/src/config.js`) creates the file with the defaults when missing, fills in fields left out, and throws a `ConfigError` naming the field for a mistake (bad JSON, wrong type, unknown field).
  - `cli/src/glob.js` compiles `*`, `?` and `**` into regular expressions. `filter()` tells files to take and folders not worth walking.
- [x] 1.2 File walk and backup (`cli/src/commands.js`).
  - `jstrace instrument <path...>` (paths relative to the current folder, inside the project) takes the files under each path that the config's filter takes, or a file named outright whatever the filter says. It doesn't follow symbolic links to folders.
  - Each original is copied to `.jstrace/backup/<path>`, and `manifest.json` records the SHA-1 of what was written.
  - Paths add up: instrumenting more keeps what's already instrumented.
  - It reports a summary on stdout (`Instrumented 7 files, skipped 1`) and each skipped file on stderr. Exit code 1 for a bad config or a path missing or outside the project.
- [x] 1.3 `jstrace restore [path...]` puts back the originals (all, or those under the paths), removing their backups and empty folders, and the backup folder once nothing's left.
  - A file changed or deleted since it was instrumented is left alone, its original kept and named in the message.
- [x] 1.4 Parsing: a file acorn can't parse as a script is skipped with `<path>: skipped, it can't be parsed as a CommonJS script (<acorn's message> (line:col))`.
- [x] 1.5 Function discovery: `cli/src/walk.js` visits every node with its ancestors, and `cli/src/instrument.js` names each function.
  - Rules: its own name; a class member's `Class->method` (`get`/`set` prefixed, `#private`, `[computed]`); or the name it's given (`const x =`, `a.b =`, `X.prototype.y =` as `X->y`, a default parameter, `obj.method` in `const obj = {…}`).
  - Anything else is `<anonymous@line:col>`, with the column counted from 1.
  - Metadata per function: `[name, line, column, params]`, with the position of the member for methods (the key, not the parentheses) and the names the parameters bind (patterns included).
- [x] 1.6 Injection (`instrumentSource()`): text insertions sorted by offset. At one offset, a node's own pieces keep their order (an empty body), closing pieces come before opening ones, inner closings first and outer openings first.
  - A block body gets `;const __jtc=__jtm.enter(i,[params]);try{` after its directives, and `}catch…finally{__jtc.exit()}` before its `}`. An arrow's expression body becomes a block returning `__jtc.ret(…)`. acorn's `preserveParens` keeps a `({…})` body whole.
  - A module's own top-level `return` is left alone.
  - The output is checked to have the same line count and to parse, else it's a jstrace bug.
  - The same tests run sources both ways and compare results (functions, classes, async, generators, a shebang, directives, CRLF, a BOM, an empty file).
- [x] 1.7 The prelude: after the shebang line and directives, `;var __jt=globalThis.__jt||(globalThis.__jt=new Function("require","options",…)(require,{options}));var __jtm=__jt.load(file,functions);`.
  - The runtime factory's source and the metadata are JSON with U+2028/U+2029 escaped, so it stays on one line.
  - `var __jtm=__jt.load(` marks a file as instrumented (`isInstrumented()`).
  - The runtime (`cli/runtime/runtime.js`) documents the API instrumented code calls. It passes everything through until milestone 2.
- [x] 1.8 Async: `await x` becomes `__jtc.r(await __jtc.sa(x))` and `yield x` becomes `__jtc.r(yield __jtc.sy(x))` (a bare `yield` yields `__jtc.sy()`). `for await` isn't touched.
  - An end-to-end test instruments the app fixture with a recording runtime: it prints the same, and every load, call, return, throw, suspend and resume is recorded, in both processes.
- [x] 1.9 Instrumenting a file again starts from its backup, so it picks up config changes and never gets code injected twice. A changed one is left alone. One with injected code but no backup (`.jstrace/` lost) is refused.

## 2. Runtime (injected prelude)

- [x] 2.1 The `globalThis.__jt` singleton (`createRuntime` in `cli/runtime/runtime.js`), one per process. It writes with `globalThis.__jstraceFs` or Node's `fs`, to the folder baked in (`options.logs`) or `JSTRACE_OUT`, as `<startTime>-<pid>.jsonl` and `.txt` (the ISO start time, with `-` for `:`).
  - The files open at the first event, starting with a `start` event (pid, argv, cwd). A failed write stops tracing with one message on stderr; the program goes on.
  - The instrumenter embeds the runtime without its comments, blank lines and indentation (`compact()` in `instrument.js`, using acorn's comments).
- [x] 2.2 Safe serializer: JSON, with what JSON can't hold as bracketed strings (`[undefined]`, `[NaN]`, `[10n]`, `[Symbol(s)]`, `[Function f]`, `[class C]`, `[Circular]`, `[Error: msg]`, `[Date …]`, `[RegExp /x/]`, `[Uint8Array(2) 1,2]`, `[ArrayBuffer(4)]`).
  - A class instance is `{"[Class]": {…}}`, or `"[Class]"` with no own properties (a Promise). Maps and Sets are `{"[Map(n)]": [[k, v], …]}` and `{"[Set(n)]": […]}`.
  - Getters and setters are named, not called. Serializing runs with tracing off, and a value that throws becomes `[Unserializable]`.
  - Past `maxDepth`, an object is `[Object]`, `[Array(n)]`, `[Class]`. Strings are cut at `maxString` (`abcde…(+3)`). A value's whole length is kept to roughly `maxLine`: arrays and objects end with `…+N more`.
- [x] 2.3 Call tracking: a stack of entries (calls and resumes). The events: `start`, `load`, `call`, `return`, `throw`, `yield`, `resume` (see Architecture for the fields).
  - Each call ends with exactly one `return` or `throw`, logged at `exit` with the value `ret` or `throw` got.
  - A suspended call that goes on is logged as a resume on top of whatever is running: a new root for an async function, inside the caller of `next()` for a generator.
  - `sa` turns an awaited promise's rejection into a value that `r` rethrows after logging the resume (one more microtask tick per `await` of a promise). A suspended generator ended by `gen.throw()` or `gen.return()` logs its resume at its next event.
- [x] 2.4 The `.txt` tree: two spaces per depth. A `start` header line, then `load file`, `name(param: value) #id  file:line`, `← value`, `← throws …`, `← yields …`, `↻ name() #id resumed  file:line`, with paths relative to the project (`options.root`).
- [x] 2.5 End-to-end tests (`test/e2e.test.js`): instrument the app fixture with the CLI and run it. Both processes' logs are checked: loads, every call ending once, every parent seen before, the factorial chain, a throw, async resumes, yields, a callback from `node_modules`, and the tree's text.
  - Then restore: every file comes back byte for byte, and the logs stay. `JSTRACE_OUT` is tested too.
  - Runtime tests (`cli/runtime/runtime.test.js`) run instrumented sources in-process with a fresh runtime. The `same()` tests in `instrument.test.js` now run with the real runtime, logging to a temp folder.

## 3. VSCode extension

- [x] 3.1 Manifest and an activity-bar container with the "Calls" tree view: projects (only with more than one) → log files (newest first, one per process, labeled by script and arguments, with start time and pid) → call tree.
  - Labels read like the `.txt` tree. A call's description is what it returned or threw in the end, even in a later resume. The hover has the arguments and value, pretty-printed. A call that threw gets a red icon.
  - `vscode/logs.js` parses the `.jsonl` (skipping a line cut short) and makes the text, with no `vscode` needed.
- [x] 3.2 Jump to code: clicking a call or load opens the original file at the function (the line is exact even while instrumented; the column may be off a little).
- [x] 3.3 Setting `jstrace.cliPath`: a `.js` script (run with VSCode's own Node via `ELECTRON_RUN_AS_NODE`) or a program (through `cmd.exe` on Windows, arguments quoted). Empty takes the CLI packed in the extension, else the repo's `cli/` beside it, else `jstrace` on the PATH (`vscode/cli.js`).
  - Later dropped: since 3.8 the CLI is packed in the extension, and the setting (overridable by a workspace) let a repo run a script of its own. The extension runs only its own CLI now, packed in it or the repo's beside it.
- [x] 3.4 "jstrace: Inject" (once "Inject jstrace") in the explorer's context menu (folders and files, several at once): runs `jstrace instrument <them>` in each one's workspace folder. It reports the CLI's summary and what it skipped; everything goes to the "jstrace" output channel.
- [x] 3.5 Restore: a view button and command running `jstrace restore` in each project with a backup, reporting files it left alone.
- [x] 3.6 Refresh and clear logs (with a confirmation) buttons. `.jstrace/` is detected in each workspace folder, and a watcher refreshes the list when logs are added or deleted. A log's inline button opens its `.txt`. A welcome text explains how to start.
- [x] 3.7 Clicking a `↻ foo() resumed` node selects the call it belongs to, and goes to the function. A call's hover says how many times it resumed.
- [x] 3.8 Local install: `npm run package` (`vscode/pack.js`, a hand-written zip with no `vsce`) builds `jstrace-vscode-0.1.0.vsix` with the CLI and acorn inside, for `code --install-extension`. A symlink isn't used, since recent VSCode only loads extensions listed in its `extensions.json`.
  - Tests: `vscode/extension.test.js` runs the extension against a fake `vscode` (inject, the tree of a real run, jumping, a resume's call, restore, clear). `pack.test.js` unzips the package and runs the CLI from it. Installing it into a separate extensions folder was checked by hand.

## 4. Later / maybe

- [x] 4.1 Repeats: `maxRepeat` in the config (default 20, 0 for no limit), instead of the proposed cap on events per process. A call (all its parts) or the top level logs its first `maxRepeat` calls of each function, and a call its first `maxRepeat` resumes (async loops, long iterations). Past that, a call or resume is muted: kept on the stack, but nothing in it is serialized or logged.
  - `skip` events give the counts, in the call's last logged part before its return (`… step() called 3 more times, not logged` in the `.txt`). The top level's, and those of calls still running, are written when the process exits.
  - Calls aren't found in loops by reading the code: only function bodies are instrumented, and repetition also comes from `.map` callbacks, timers and events, so calls are counted while the program runs.
- [x] 4.5 Grouping in the tree view (setting `jstrace.groupRepeats`, default 5, 0 for none): under one node, the calls of a function made that many times (or with some skipped) become one row, `step() ×1003` with `3 not logged, 1 threw`, where the first call was. The resumes of a function's calls group the same way (`↻ double() resumed ×6`). A skip without a group is a row of its own. A resume in a group still reveals its call.
- [x] 4.6 Show Details: a call's (or a group's) details in a read-only `jsonc` tab beside, for when the hover isn't enough: where and when it ran, how long it took, the calls it ran in, its resumes, then its arguments, outcome and yields, pretty-printed. A resume shows its call's; a group lists each of its calls. Inline on hover, in the context menu, and in the command palette (for the selected item).
- [x] 4.7 Expand All Below (context menu): expands an item's whole subtree, level by level, with a progress bar in the view.
- [x] 4.12 Call sites: each call logs where it was called (`site`, from the stack trace; `callSites` in the config, on by default), shown as `(from index.js:26)` in the `.txt`, in hovers and details. In the tree, clicking a call goes to its call site, with the cursor on the callee's name there (`math.factorial(` rather than a `'factorial(5)'` text before it); an inline button and the context menu go to the function. Works with Node 12's stack format too, and the injected code was made Node 12-safe (no `??`), with a test parsing it as ES2019.
- [x] 4.2 Live tailing: the tree view follows a log as it's written. Every second, each listed log is read from where the last read stopped, up to its last complete line, into the same trees (`readMore`), and only a log that grew is refreshed, so what's expanded stays expanded. A log whose process still runs gets a spinning icon and `running`, and its unfinished calls `running…`. The playground's `slow.js` runs for about 15 seconds to watch it.
- [x] 4.3 Search: a "Search" view under Calls (and a search button on Calls) finds the calls and loads in every log whose name with its arguments, outcome, or `file:line` has all the words searched, ignoring case (`search` in `logs.js`). Results are listed per log in the order they ran (the first 1000 of each), with the words highlighted, and searched again as the logs grow. A click goes to the code as in Calls; a double-click (or the inline button) shows the call in the Calls view, expanding what it ran in. Resumes aren't listed, being parts of their calls. Filtering the Calls tree itself was left out: VSCode's own find in a tree (Ctrl+Alt+F) filters what's expanded.
- [x] 4.10 Step through a run, like a debugger after the fact, from the selected call (or log, or group) in the Calls or Search view, with keys while either view has the focus: Step Into (the next call, whatever it ran in) `Alt+↓`, Step Back `Alt+↑`, Step Over (the next call not inside this one) `Alt+Shift+↓`, Step Back Over (the previous one at this level, or the caller) `Alt+Shift+↑`, Step Out (to the caller) `Alt+←`; the same `⌥` keys on macOS, whose `Ctrl`+arrows belong to Mission Control. Also a "Step" submenu in the context menu. Each step selects the call in the Calls view and shows where it was called (its code, without a site), with the line highlighted like a debugger's and the call with its outcome at the end of it. The view keeps the focus, so the keys go on working, and they're never taken from the editor (where `Alt+↑/↓` move lines). Since a step lands on the call site, into/over/out read as in a debugger: into goes inside the call, over to the next call in the same function, out to the line that called the function. A left click on a call shows it the same way, so stepping starts from wherever one clicks. `Esc` (in the views, or in the editor when it has nothing else to do), a click on another line, or "Hide Step Highlight" hides the highlight.
  - Later, the setting `jstrace.stepHint` placed the values: `above` the line (the default, a CodeLens that opens the details; at the end where CodeLens is off), at its `end`, or only on `hover`. Hovering the line shows the call's tooltip in all three. The colors are the theme colors `jstrace.stepBackground` and `jstrace.stepForeground`.
- [x] 4.13 External calls (config `externalCalls`, off by default): calls made from instrumented code to functions that aren't traced (built-ins like `JSON.parse` or `arr.map`, Node's `fs.readFileSync`, a package that isn't instrumented) are logged as call nodes, named by the callee as written, with their arguments by position and outcome, and the traced callbacks they run nested inside them. Callees matching `ignoreCalls` (`console.*`, `Math.*`, `*.push`, … by default) are left alone. In the extension they have their own icon, and Go to Call Site but no Go to Function.
- [x] 4.14 Merge the logs of processes into a new one, to follow how they talk: "Merge Logs…" on logs selected together in the Calls view, or a checklist from its title bar. Events in the order they happened across the processes, each call's label starting with its process's name and pid (`server 1234 › send()`) and its icon colored per process; a `.txt` with each line after its process. "Name Process…" names a log's process (shown in its label); merging asks for the names not given yet.
- [x] 4.15 Mocks: everything the injected code takes from its environment (the log writes, environment variables, pid, command line, working folder, clock, start time, call sites, the exit, its messages) can be replaced, by `globalThis.__jstraceMock` or the module the config's `mock` names. `jstrace mock` (and the extension's "Create Mock") makes one from a template listing every hook. Also README.md, the user's guide.
- [x] 4.16 "jstrace: Find Calls at This Line": an editor context-menu command (and in the command palette) listing in the Search view the calls at the cursor's line, in every log: those made from it (by call site, or an external call made there) and those of a function defined on it (`searchAt` in `logs.js`). Paths are compared ignoring case on Windows.
- [x] 4.17 Init: `jstrace init` creates `jstrace.config.json` with the defaults (one there already is only checked) and `.jstrace/` with its `.gitignore`, so the config can be edited before anything is instrumented. In VSCode, "jstrace: Init" (in the command palette, and a button in the empty Calls view) runs it in the workspace folder and opens the config. It was on folders in the Explorer too, until the user had it taken off the context menu.
- [x] 4.19 Logs readable on another machine: files in the project are logged relative to it (case ignored on Windows), and the extension resolves them against its workspace folder; `start` has the project's `root`, and an `end` event (with the exit code) marks a process that ended, so a copied log isn't shown as running. Also README.md (Reading logs on another machine).
- [x] 4.23 Reinject: `jstrace reinject` (and "jstrace: Reinject" in the command palette) instruments again the targets instrumented since the last time all was restored, recorded in `.jstrace/injected.json`; once all is restored the list is kept for reinjecting and the next `instrument` starts a new one. New files in recorded folders are taken; paths gone since are skipped. A partial restore leaves the list as it is.
- [x] 4.22 Call-site code: Inject bakes the code of each line making a call (trimmed, cut at 200 characters) into the file's `load` call, and a call made there logs it as `site.code` (an external call as `code`). Search looks in it, so a call is found by the names of the variables passed to it; the hover and Show Details show it ("called as"). Only lines that start a call, or hold a method's name, are kept (a getter's site has none), and not at all with `callSites` off unless external calls are on. The user chose recording at Inject over reading the source when searching (exact after edits, and on another machine).
- [x] 4.25 Inject can't lose track of what it rewrote, and the extension always works in its workspace folder. The extension no longer limits the CLI's output (Node killed it past 1 MiB, midway through a big `node_modules`, leaving files instrumented with no manifest), and `instrument` keeps a journal beside the manifest, so a run killed any other way stays restorable. `--project <folder>` names the project, and the extension always passes it, so a stray or planted `.jstrace/` above a workspace folder can't take over. On the console the search upwards stays. From an independent review of the whole project, whose other findings need a hostile repo or log, which the user doesn't have.
- [x] 4.20 Logs from others are untrusted (since 4.19 they're meant to be passed around). All that a log says goes into a hover escaped or in a code block, so a crafted one can't load a remote image on hover. A network path it names is opened only inside a workspace folder, so a click can't make Windows authenticate to another host; only paths known to be local pass freely, since a network path has too many spellings to list.
- [x] 4.24 Show by Time: a button in the Calls view's title bar lists each log's records at one level, in the order they happened, instead of as call trees: calls, resumes, loads and calls not logged, with no groups, for following how processes talk (most of all in a merged log). A clock button shows or hides each row's timestamp, by the local clock. Both are kept for the workspace. A call's return stays on its row rather than being a row of its own. A log past 2000 records is split into pages, like big arrays in a debugger, so a view can't freeze on a huge one and every row can still be revealed.
- [x] 4.21 Delete Log: deletes one log (or all those selected) from the Calls view, with its `.txt` and its process's name, after a confirmation that warns when its process still runs. In the log's context menu, and on `Delete` (`Cmd+Backspace` on macOS) while the view has the focus.
